# The feedback system, in two PRs (2026-09-06)

The owner asked on 2026-09-06 for a feedback system as the immediate item (D-557). A user gives a thumbs up or a thumbs down on four things: a question, a deck description, one card, and a whole deck. A thumbs up shows the toast "Thank you for your feedback!". A thumbs down darkens the screen and opens a dialog with prefilled reasons for that kind of item and an "Other" text box. Submit shows the same toast.

Then the product addresses the feedback in a semi-autonomous way. An agent reads it, turns it into test cases, and proposes a fix, and the owner merges. Two PRs carry it: PR-27 harvests the feedback, and PR-28 addresses it.

This note holds the design of both, the defaults this session chose, and the three questions for the owner.

## 2. PR-27, the harvest

### 2.1 The contract

`proto/mtg/v1/feedback_service.proto` adds one service with one RPC: `FeedbackService.SubmitFeedback`. The request holds one `Feedback` message:

| Field | Meaning |
|---|---|
| `kind` | `QUESTION`, `SUMMARY`, `CARD`, or `DECK` |
| `verdict` | `UP` or `DOWN` |
| `session_id`, `question_id` | The question, for kind `QUESTION` |
| `deck_id` | The deck, for `SUMMARY`, `CARD`, and `DECK` |
| `oracle_id` | The card, for `CARD` |
| `reasons` | The keys of the prefilled options the user checked, for a thumbs down |
| `text` | The "Other" text, at most the message cap of the chat |

The response holds the id of the stored feedback. There is no list RPC: the harvest of PR-28 reads Firestore with the owner's credentials, as `make allow` does (D-420).

### 2.2 The store

One document per item under `users/<uid>/feedback/<id>`. It holds the fields above, `created_at`, and the versions of the classify, ask, and generate prompts at the time of the verdict. The versions tell PR-28 which prompt the user judged. The API checks that the session or the deck belongs to the caller before it writes, so a feedback item never names another user's object. `make store-check` runs its emulator test with the other five stores.

### 2.3 The screen

`web/apps/web/src/features/feedback` is a leaf feature. It holds `Thumbs`, two icon buttons with the labels "This helped" and "This missed", and `FeedbackDialog`. The chat, the deck, and the workspace features import it, and the import boundary of `eslint.config.js` names it.

| Where | What the thumbs judge |
|---|---|
| Under the text of a question card, open or answered | The question |
| Beside the summary paragraph in the deck header | The deck description |
| At the foot of every card tile, and in the card detail sheet | One card |
| In the deck header, beside the legality line, with the label "Rate this deck" | The deck as a whole |

A thumbs up submits at once and shows the toast "Thank you for your feedback!". A thumbs down opens the dialog. The dialog dims the screen, names the item, and offers the reasons of the kind as check boxes, then an "Other" box for free text. Submit opens when the user checks one reason or types in the box. Submit writes the feedback and shows the same toast. After a verdict the two buttons show the chosen state and take no second click on this page.

### 2.4 The prefilled reasons

| Kind | Reasons |
|---|---|
| Question | You already had this answer. The question does not apply to my request. The options are wrong, or one is missing. The wording is unclear. |
| Deck description | It claims something the deck does not do. It misses the plan I asked for. It is too long or too vague. |
| Card | This card does not fit the theme. This card breaks the format or my house rules. I do not own it and did not want to buy. This is the wrong printing. It is too weak or too strong for the bracket. |
| Deck | It does not match what I asked for. The mana base is off. Too little interaction, ramp, or draw. Too weak or too strong for the bracket. Too many cards to buy. |

Every kind ends with "Other". Each reason has a stable key, and PR-28 reads the keys.

### 2.5 The gate

- Every placement has a unit test, and the dialog passes axe.
- The emulator test of the store passes under `make store-check`.
- The API refuses a deck id or a session id of another user with `PermissionDenied`.
- The smoke flow of PR-23 gives the built deck a thumbs up and reads the toast.
- Every thumbs button is 44 pixels or more on a touch screen, so the phone gate of PR-25 finds nothing here.

The gate is free. No step calls a model.

## 3. PR-28, the loop

### 3.1 The shape

Three steps, and the owner starts each cycle by hand.

1. **Harvest.** `make feedback-harvest` reads every feedback item since the last harvest, with the owner's credentials. It writes one dated document under `docs/reference/feedback/` and one JSONL file beside it. Each item carries its context: the session turns, the slots, the deck list, and the prompt versions.
2. **Triage.** The judge role reads each thumbs-down item and names its class and its target artifact, from the table below. A thumbs-up item becomes a keep case: a change must not flip it.
3. **Propose.** The fixer agent of the tuning loop runs on a branch of its own with the new cases. The gate that owns the case measures the change, under a cap. The result is a pull request with the evidence document, and the owner merges or closes it.

### 3.2 The triage classes

| Class | The user's words | Artifact the harvest writes | Where the fix lives |
|---|---|---|---|
| Q1, asked again | "You already had this answer" | A conversation in `conversations.json` with the user's messages and a "must not ask" expectation | The catalog trigger, the word rules, the classify prompt |
| Q2, off target | "The question does not apply" | The same, with the row named | The catalog `when` clause |
| Q3, bad options | "The options are wrong" | The same, with an option expectation | The resolver and the hints |
| S1, false summary | "It claims something the deck does not do" | A summary judge case (F-26) | The generate prompt |
| C1, off theme | "This card does not fit the theme" | A deck gate prompt from the slots, with a "no card X" assertion | The candidates ranking, the tags, the lint |
| C2, illegal | "This card breaks the format" | A rules test | The rules engine, a code fix and never a prompt |
| C3, unwanted buy | "I did not want to buy" | A deck gate prompt with the pool rule and an ownership assertion | The pool and the generate prompt |
| D1, off spec | "It does not match what I asked for" | A deck gate prompt from the slots, with the golden expectation of the user's words | The classify prompt and the build |
| D2, bad mana | "The mana base is off" | A deck gate prompt with the band of the profile | The targets and the profile |
| D3, bad power | "Too weak or too strong" | A bracket gate prompt | The profile and the bracket rules |

A "must not ask" expectation is new. Today an expectation names the value a slot must end with. This one names a row that must not fire. The gate reads it as one more row.

### 3.3 The guards

Every guard of the tuning loop holds. They are the branch of its own, the frozen files, the append-only decisions, and the green build. They are also the holdout, the noise margin, the lessons file, and the owner-questions rule. Two guards are new.

- The harvest file names the user by the uid and the session id, never by the email (D-559). The user's own words and the deck list stay, because the agent needs them. The file lives in the repo of the owner alone, and no case that enters `conversations.json` or `prompts.json` carries a uid.
- A class that meets an owner decision stops. A user who disagrees with a bracket rule of D-459 raises an owner question. The loop writes it to `docs/owner-questions.md` and makes no fix.

### 3.4 Cost and cadence

The harvest and the triage cost cents: one judge call per thumbs-down item. A fix cycle costs one gate run: $0.19 for the question gate, or about $0.15 per deck gate prompt with `-only`. The fixer's own model calls come on top, outside the ledger of this repo. No step runs in CI, because the Actions minutes are scarce (D-286) and every step spends money. The owner runs `make feedback-loop` on demand, and one cycle stops at $2 of gate runs (D-559).

### 3.5 The gate

- A harvest over the emulator with ten seeded items writes the document, the JSONL file, and the cases.
- A dry triage over a fixture of ten items, the owner's own past complaints, names the expected class of each.
- One live cycle on the owner's word ends with a pull request and a passing gate on its new cases. `make eval-check` shows no flip on the baselines.
