## Findings

### P2-1: Creation writes can move the timestamps backwards

Status: open.

Open at: `6ac5e7ae3e394f6666b8ad6fb27df5982567a991`.

File: `go/internal/users/users.go:150-156`.

Trigger: Two operations for one user capture times `t2` and `t1`. `t1` is earlier, but its write commits last. The paths call `NoteQuietly` with per-request `s.now()` values. Parallel deck, chat, upload, and verdict operations can overlap.

Expected: D-1093 defines `last_seen_at` and `last_creation_at` as the newest activity and newest deck or chat. Each field must retain its maximum timestamp.

Actual: `Note` assigns `last_seen_at = at` for every counter and assigns `last_creation_at = at` for deck and chat counters. The later commit of the older event overwrites the newer time. `Touch` and `Seed` already guard their timestamp updates with `After`, but `Note` does not.

Consequence: The stored record can report an older last activity or creation than the user actually made.

Correction: Make the timestamp writes monotonic under concurrent `Note` calls. Add a regression test that applies an older event after a newer one for both fields.

Regression check: The new test must fail against this head and pass after the correction. Rerun the relevant user tests and `make verify`.
