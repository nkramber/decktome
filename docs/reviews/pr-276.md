## Findings

### P2-1: Creation writes can move the timestamps backwards

Status: fixed in `99dd96fd5b0eaa1d477500f2c02886d60e8ec2ee`.

Open at: `6ac5e7ae3e394f6666b8ad6fb27df5982567a991`.

File: `go/internal/users/users.go:150-156`.

Trigger: Two operations for one user capture times `t2` and `t1`. `t1` is earlier, but its write commits last. The paths call `NoteQuietly` with per-request `s.now()` values. Parallel deck, chat, upload, and verdict operations can overlap.

Expected: D-1093 defines `last_seen_at` and `last_creation_at` as the newest activity and newest deck or chat. Each field must retain its maximum timestamp.

Actual: At the earlier head, `Note` assigned both timestamps without a read. The correction reads the record in a transaction and writes a timestamp only when it is newer. It also copies the version 1 timestamp before it updates the record to version 2.

Consequence: The earlier code allowed an older timestamp to replace newer activity or creation time. The current transaction prevents this result.

Correction: The transaction and the monotonic timestamp checks in `Note` correct the finding.

Regression check: `TestALateNoteNeverMovesATimeBack` and `TestNoteMovesARecordOfVersionOne` pass in `make verify` and in the effective-head CI verify jobs.
