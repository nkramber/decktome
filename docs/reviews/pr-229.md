## Findings

### P2-1: Delete can remove a session after a build acquires its lease

Status: fixed in `a8efdf3206159d9866843bb792e6a202f4b1d0e6`.

Open at: `4d51d4c58daad5ec68de1d7916bb95a5b3c9da98`.

File: `go/internal/agentsvc/sessions.go:155-170`.

Trigger: A delete reads no lease. Before its later delete transaction, a ready chat acquires the lease and stores its turn. The delete transaction then removes the session and lease while the build runs.

Expected: D-922 requires a delete on any instance to refuse while a build holds the lease. The check and delete must act on one consistent store state.

Actual: `DeleteSession` calls `Leased` before `Get` and `Delete`. `Repo.Delete` then deletes the session and lease in a transaction with no lease check. A lease acquired after the first read does not stop deletion.

Consequence: The build can finish after the session and lease disappear. `storeDeck` can keep the new deck, then fail to record its id because the session no longer exists. The user can see a deck from a session they deleted during its build.

Correction: Check the lease in the delete transaction, and reject a live lease. Add a test that pauses deletion after its lease read. Start a build on another server. Prove deletion leaves the session and lease intact.

Regression check: `TestADeleteRefusesALeaseTakenAfterItsRead` now takes a lease after the earlier reads and checks that deletion keeps the session and lease. `TestEmulatorBuildLease` checks that a live lease blocks the transactional delete. Both pass at `a8efdf3`.
